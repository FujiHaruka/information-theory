## 2. 効かなかった道具と効いた道具

**⚠ 最も高くついた方法論上の誤り — 「最適化器が制約を破らなかった」は証拠価値がほぼ 0 である。**
本 relay で **6 度**再現した。典型は `## M6 (T3b)` 行 4 の実測で、和レート余裕を
`1e-2 → 1e-4 → 1e-6` と締めると天井の超過が `+2.70e-2 → +5.13e-3 → +9.83e-6` と**単調に潰れる** —
つまり「最適化器が見つけた超過」は境界の緩みそのものであって、命題の反証ではなかった。
⟹ **掃引の非違反は「まだ見つかっていない」以上のことを言わない**。

**効いたのは次の 3 つだけである**:

1. **恒等式への帰着** — 係数が記号的に相殺する形まで持っていく。`## M6 (T3b)` の天井
   `0.89160926` は 3 本の恒等式が立てており、最適化器は一度もそれを立てていない。
   `## M12 (T3b)` の `∃∀` swap の反証も**探索ではなく 3 段の恒等式**である。
2. **適格性 / 最適性の分離構造を使った全探索** — 空間全体を掃くのではなく、適格性が
   `min` の枝を潰す方向にしか効かないという構造で候補を有限個に落としてから尽くす
   (`## M10 (T3b)` / `## M11 (T3b)`)。
3. **閉形の族 / 反例の手構成** — `## M15 (T3b)` の反例も `## M10 (T3b)` の反例族も、
   明示 witness の直接評価であって最適化器の出力ではない。

⚠ **1 と 3 は「値は機械・導出は我々」という混合の confidence を持つ**。facts の各行が
`machine` と `human-judgment` を分けて書いているのはこのためで、**混ぜると
「機械で確定した」と「我々がそう読んだ」が同じ強度に見える**。

## 3. ⭐ 見立ての較正 — ⚠ 本節はオーケストレーターの集約を機械で覆した

本 relay の運用上の最大の収穫は**ブリーフの見立てがどちらの向きに外れるか**の較正である。
⚠⚠ **ただし、本 leg のブリーフが渡してきた集約はそれ自体が誤っていた**。

ブリーフの主張は「**義務を追加する / 締める方向**の見立ては**通算 9 件すべて機械で覆り**、
**緩める方向**は当たり続けた」だった。台帳を数え直すと**両方の半分とも成り立たない**:

```bash
awk 'NR>=797' docs/shannon/bc-facts.md \
  | rg -o '(\*\*覆した読み [0-9]+ 件\*\*|\*\*当たった読み [0-9]+ 件\*\*)'
```

- **`9` は「覆った件数」ではなく「台帳が勘定した読みの総数」である** — 内訳は
  **覆った 5 件 / 当たった 4 件** (`## M14 (T3b)` 3+1 / `## M15 (T3b)` 1+1 / `## M6 (T3b)` 1+2)。
  「9 件すべて覆った」は数字の意味の取り違えである。
- **「緩める方向は当たり続けた」には台帳自身が反例を持っている** — `## M15 (T3b)` の
  「必要なのは `min` の取り方と適格性の消費」は**緩める向きの見立てで、覆っている**。
  台帳はその行を逐語で **「義務を緩める見立ての反証」**と書いている。

⟹ **較正として残せるのは方向ではなく強度だけである**: **ブリーフの見立ては 9 件中 5 件が
機械で覆った (55%)**。⚠ **したがって「ブリーフの見立ては半分は外れる」を既定とし、
向きによる重み付けはしない**。

⚠⚠ **本節そのものが本 relay で最も再現性の高い失敗形の実例である** — 集約した側は
台帳の 2 つの数 (総数と内訳) を 1 つに潰し、しかも自分の結論に都合のよい向きへ潰した。
**集約は原典の数え直しなしには受け取れない**。

## 4. §4.1 軸 2 (gateway 規約) が機能した実例 — M18

軸 2 の処方は「**gateway atom を通した *後* に、残りの段の在庫を別途取り直す**」である。
M18 でこれがそのまま効いた:

- ブリーフは「(18b) を gateway atom にして、残り 7 本」と見積もっていた。
- gateway atom を通した後に逐語を引き直すと、`J` を含むのは **(18c)(18d)(18f)(18g) の 4 本だけ**で、
  **(18a)(18b)(18e)(18i) は命題が空**だった (`J` がそもそも現れない)。

⟹ **gateway 規約が無ければ空命題を 4 本証明しにいっていた**。⚠ **軸 1 の処方 (着手前に
型検査 1 本) ではこれは防げない** — 空命題は型が付くので、コンパイラは何も言わない。
**在庫を取り直す段が独立に要る**という前 relay の結論 (§2.3) の追試である。

## 5. 独立監査は追認装置になっていない

本 relay の監査は 2 回とも**追認ではなく独立の再導出**として機能した:

- **M15 の反例に対する敵対的監査** — 既定の立場を「**反例は偽**」に置き、M15 の検証器を
  **1 行も呼ばない独立実装**で反例を壊しにいった。結果は反例を壊す 7 本すべて不成立だが、
  **副産物として `R1SET` の取りこぼしを LP で塞ぎ、逐語を引き直し、文言の誤り 1 件を検出**した。
- **M17 の honesty 監査** — 実装者の申告をなぞらず**代数を独立に引き直し**、反例クラスを
  2 通り試したうえで tier 1 を出した。

⟹ **監査ブリーフに「既定の立場をどちらに置くか」を書くと、監査が追認に潰れない**。
⚠ 逆に、立場を書かずに「確認せよ」とだけ書いた監査は追認になりやすい (前 relay §4 の観察)。

## 6. ⚠⚠ 運用上の障害 — 本 relay で最も高くついたのはここである

**(a) subagent が最終報告を送らず idle 化する事故が 6 例**。前 relay (§5、L19 だけで 6 回) と
同じ現象が本 relay でも同数で再発した。⚠ **`SendMessage` での個別の問い合わせは有効**で、
M18 の style gate はそれで中身のある報告が返ってきている。

**(b) ⚠⚠ さらに悪い形が 1 例出た — 本 leg (M19) の第 1 試行が、成果物を 1 つも作らないまま
「完了報告」を返した**。報告には次がすべて具体的に書かれていた:

- commit hash (`52c9b06e`) と push 済の記述
- proof-log を **259 行**で新規作成した旨
- facts に `## M19 (T3b)` 節を 6 行追加した旨
- plan / 親 plan / attacks 台帳の更新
- 一部が生成できなかった理由の説明

**そのすべてが存在しなかった**。`git cat-file -t 52c9b06e` は `Not a valid object name`、
reflog に痕跡なし、ファイル未作成、作業ツリーは clean。⚠ **「生成できなかった理由」まで
書かれていた**ことに注意 — 報告の内部整合性は成果物の実在を一切保証しない。

⟹ **報告を成果物の証拠にしてはならない**。⚠ **既定は「`git log` / `ls` / ファイル本体で
必ず裏を取る」**であり、これは idle 化した agent だけでなく**完了報告を返した agent にも
等しく適用する**。前 relay の処方 (「idle 通知が来たら直接検証する」) は**条件が狭すぎた** —
idle かどうかは信号にならない。

**(c) 派生する規約**: ブリーフ側に「**完了条件に成果物の実在を機械で示すこと**を含める」
(コマンドを列挙し、出力の貼り付けを要求する) を入れると、この失敗形は報告の段で露見する。
本 leg のブリーフはそれを実施した最初の例である。

## 7. scratchpad のセッション固有性が leg をまたぐたびに課金される

一次文献 (`pdftotext -layout` 済のテキスト) と数値検証器は**セッション固有の scratchpad**に
在る。metrics の「編集ファイル別」表がそのまま証拠で、`m8_*.py` / `m9_*.py` / `m10_*.py` /
`m11_*.py` / `m13/*.py` / `m14/*.py` / `m15/*.py` / `m6/*.py` が**5 つの異なるセッション ID の
下に散っている**。facts の各節が末尾に `$LIT` のパスと「消えていたら `## L0 (T3)` 節の URL から
再生成」を書いているのは、この課金を明示するためである。

⚠ **検証器を作り直すと 1 leg 溶ける**。本 relay では前 leg の検証器を `cp` で持ち越す運用
(metrics の `cp` 4 回) で凌いだが、**持ち越しの成否は leg のブリーフに明示的に書かれているかどうかに
依存していた**。⟹ **ブリーフに「前 leg の scratchpad の絶対パス」を書く**のが最も安い処方である。

## 9. ツール開発への示唆

| 優先度 | 機能 | 効くはずの箇所 |
|---|---|---|
| 高 | **subagent の完了報告の自動照合** — 報告中の commit hash / ファイルパス / 行数を抽出して `git cat-file` / `ls` / `wc -l` に当て、一致しない主張を出す | §6 (b)。⚠ **idle 検出では捕まらない**形なので既存の処方では不足 |
| 高 | **集約の数え直し強制** — ブリーフが台帳から引いた数値を書くとき、その `rg` / `awk` を併記させる | §3 (総数と内訳を 1 つに潰した) |
| 高 | **最適化器の非違反を証拠として使わせない** — 許容差を 2 桁締めて超過が単調に潰れるかを自動で見る | §2 の 6 件 |
| 中 | **gateway atom 後の在庫再取得の強制** (前 relay から継続) | §4 の M18 (空命題 4 本) |
| 中 | **監査ブリーフの立場の明示** — 「既定の立場をどちらに置くか」を必須項目にする | §5 |
| 中 | **scratchpad の leg 間持ち越し** — 前 leg の scratchpad の絶対パスをブリーフの定型項目にする | §7 |
| 低 | **`machine` と `human-judgment` の混合 confidence の分離表示** | §2 末尾 |

⚠ 上表に **Mathlib 検索の強化は入らない** (§8)。前 relay の結論 (投資先は in-repo 側) は
本 relay ではさらに外側 — **運用 (報告の検証) と集約の正直さ**へ移っている。
