## 2. 効かなかった道具と効いた道具

**⚠ 最も高くついた方法論上の誤り — 「最適化器が制約を破らなかった」は証拠価値がほぼ 0 である。**
本 relay で **6 度**再現した。典型は `## M6 (T3b)` 行 4 の実測で、和レート余裕を
`1e-2 → 1e-4 → 1e-6` と締めると天井の超過が `+2.70e-2 → +5.13e-3 → +9.83e-6` と**単調に潰れる** —
つまり「最適化器が見つけた超過」は境界の緩みそのものであって、命題の反証ではなかった。
⟹ **掃引の非違反は「まだ見つかっていない」以上のことを言わない**。

**効いたのは次の 3 つだけである**:

1. **恒等式への帰着** — 係数が記号的に相殺する形まで持っていく。`## M6 (T3b)` の天井
   `0.89160926` は 3 本の恒等式が立てており、最適化器は一度もそれを立てていない。
   `## M12 (T3b)` の `∃∀` swap の反証も**探索ではなく 3 段の恒等式**である。
2. **適格性 / 最適性の分離構造を使った全探索** — 空間全体を掃くのではなく、適格性が
   `min` の枝を潰す方向にしか効かないという構造で候補を有限個に落としてから尽くす
   (`## M10 (T3b)` / `## M11 (T3b)`)。
3. **閉形の族 / 反例の手構成** — `## M15 (T3b)` の反例も `## M10 (T3b)` の反例族も、
   明示 witness の直接評価であって最適化器の出力ではない。

⚠ **1 と 3 は「値は機械・導出は我々」という混合の confidence を持つ**。facts の各行が
`machine` と `human-judgment` を分けて書いているのはこのためで、**混ぜると
「機械で確定した」と「我々がそう読んだ」が同じ強度に見える**。

## 3. ⭐ 見立ての較正 — ⚠ 向きによって外れ方が**非対称**である

本 relay の運用上の最大の収穫は**ブリーフの見立てがどちらの向きに外れるか**の較正である。
⚠ **結論は 2 本立てで、1 文に畳めない**。

**⚠⚠ 母集団の取り方を先に固定する (これを書かないと下の 2 つの数が合わなくなる)。**
本節が数えるのは **`## M8 (T3b)`–`## M18 (T3b)` の各節が「ブリーフの見立て」として名指しした読み**
であり、`## M14 (T3b)` / `## M15 (T3b)` / `## M6 (T3b)` の 3 節だけが持つ勘定行
(「覆した読み N 件 / 当たった読み N 件」、合計 9) とは**母集団が違う別の 9** である。混同しない。

```bash
# 3 節の勘定行 (= 別勘定。合計 9 = 覆った 5 + 当たった 4)
awk 'NR>=797' docs/shannon/bc-facts.md \
  | rg -o '(\*\*覆した読み [0-9]+ 件\*\*|\*\*当たった読み [0-9]+ 件\*\*)'
```

### 3.1 義務を追加する / 締める方向 — **9 件、9 件とも機械で覆った**

| leg | ブリーフが締めた見立て | 実測 |
|---|---|---|
| M8 | 領域レベルの増強単調性 `Thm7(T) ⊆ Thm7(T')` が要る | **義務ではない** (M8 行 1) |
| M9 | 連鎖律の段が懸念 | **無条件に成立** |
| M11 | 緩和版では剛性が崩れる | **誤り** — `𝒞` が凸なので剛性はそのまま生きる (M11 行 3) |
| M12 | `## M7 (T3b)` 行 5 の射程限定 (i) (積入力・積 `W`) が要る | **不要** — 限定なしで立つ (M12 行 1 / 行 3) |
| M13 | `(const,const)` と `(const,X)` の 2 対に同一 witness が要る | **義務ではない** — 移送はインスタンスごとに独立 |
| M14 | `Sa` が最初の障害 | **`R₀ = 0` では義務が空** |
| M14 | `p` 共有 (`d*`-argmax 入力での退化) が先決事項 | **射程外で消える** |
| M18 | 段 1 = (18b) の `J`-free 化 | **逐語では命題が空** ((18b) は `J` を含まない) |
| M18 | 残り 7 本 | **逐語で `J` を含むのは 4 本だけ** |

⟹ **締める方向の見立ては、母集団を明示したうえで 9/9 で覆る**。⚠ **例外が 1 件も無い**のは
本 relay で唯一の全件一致であり、処方として使える強度がある。

### 3.2 義務を緩める方向 — **当たり 3 / 外れ 5 で、⚠ 外れの方が高くついた**

- **当たり (3)**: M14 (Thm8 の `p` は `∃` の内側) / M17→M18 (**必要な橋は 4 本とも 0 本**) /
  M6 (経路 1 と経路 2 は一致する)。
- **外れ (5)**: M11 (時分割 gluing で貼れる → **恒等式で死亡**) / M11 (選択原理・単調性・凸性の路
  → **チャネル固有の構造を使わない限り閉じない**) / M12 (`∀J` が有限個の極点条件に落ちる →
  **落ちない**) / **M15 (`min` の取り方で買える → 買えない。⚠ 台帳がその行を逐語で
  「義務を緩める見立ての反証」とタグしている)** / M6 (単一対の領域 `=` Cor 4 という強い読み →
  正しくは `⊇`)。

⚠ **外れの方が高くついた** — 締める側の外れは「要らない義務を用意した」で済むが、緩める側の外れは
**その見立ての上に leg を組んでから死ぬ**。M11 の時分割 gluing と M15 の `min` はどちらも
leg の主戦力として設計されていた。

### 3.3 ⚠ 書いてはならない結論

⚠⚠ **「緩める提案は当たりやすい」とは書かない**。3.2 のとおり緩める方向は**当たりも外れもあり**、
しかも外れの方が高い。**非対称なのは「締める方向が全件覆る」という一方だけ**である。

⟹ **処方**: **締める見立ては疑ってかかる (9/9 で覆っている)**。**緩める見立ては、当たれば安いが
外れると leg ごと持っていかれるので、着手前に §2 の 3 つ (恒等式 / 構造つき全探索 / 手構成) の
どれで殺せるかを先に決める**。⚠ **どちらの向きも「そのまま採用」は既定にしない**。

## 4. §4.1 軸 2 (gateway 規約) が機能した実例 — M18

軸 2 の処方は「**gateway atom を通した *後* に、残りの段の在庫を別途取り直す**」である。
M18 でこれがそのまま効いた:

- ブリーフは「(18b) を gateway atom にして、残り 7 本」と見積もっていた。
- gateway atom を通した後に逐語を引き直すと、`J` を含むのは **(18c)(18d)(18f)(18g) の 4 本だけ**で、
  **(18a)(18b)(18e)(18i) は命題が空**だった (`J` がそもそも現れない)。

⟹ **gateway 規約が無ければ空命題を 4 本証明しにいっていた**。⚠ **軸 1 の処方 (着手前に
型検査 1 本) ではこれは防げない** — 空命題は型が付くので、コンパイラは何も言わない。
**在庫を取り直す段が独立に要る**という前 relay の結論 (§2.3) の追試である。

## 5. 独立監査は追認装置になっていない

本 relay の監査は 2 回とも**追認ではなく独立の再導出**として機能した:

- **M15 の反例に対する敵対的監査** — 既定の立場を「**反例は偽**」に置き、M15 の検証器を
  **1 行も呼ばない独立実装**で反例を壊しにいった。結果は反例を壊す 7 本すべて不成立だが、
  **副産物として `R1SET` の取りこぼしを LP で塞ぎ、逐語を引き直し、文言の誤り 1 件を検出**した。
- **M17 の honesty 監査** — 実装者の申告をなぞらず**代数を独立に引き直し**、反例クラスを
  2 通り試したうえで tier 1 を出した。

⟹ **監査ブリーフに「既定の立場をどちらに置くか」を書くと、監査が追認に潰れない**。
⚠ 逆に、立場を書かずに「確認せよ」とだけ書いた監査は追認になりやすい (前 relay §4 の観察)。

## 6. ⚠⚠ 運用上の障害 — 本 relay で最も高くついたのはここである

**(a) subagent が最終報告を送らず idle 化する事故が 6 例**。前 relay (§5、L19 だけで 6 回) と
同じ現象が本 relay でも同数で再発した。⚠ **`SendMessage` での個別の問い合わせは有効**で、
M18 の style gate はそれで中身のある報告が返ってきている。

**(b) ⚠⚠ 報告と実態が乖離した例が 1 件出た — 記録 leg (M19) の担当 `m19-record` の最初の完了報告**。
⚠ **以下は観測された事実のみで、原因は書かない**。

**報告が主張したもの**: commit hash (`52c9b06e`) と push 済 / proof-log を **259 行**で新規作成 /
facts に `## M19 (T3b)` 節を 6 行追加 / plan・親 plan・attacks 台帳の更新 /
**metrics は生成できなかった旨とその理由**。

**検証時点の実態** (乖離は**両方向**に出た):

- `git cat-file -t 52c9b06e` → **`Not a valid object name`**。reflog に痕跡なし。
- proof-log ファイルは**未作成**。facts に `## M19 (T3b)` 節は**無し**。作業ツリーは **clean**。
- ⚠ **逆向きの乖離が 1 件**: 報告が「生成できなかった」とした **metrics の 3 本は実際には
  ディスク上に存在した** (未追跡。内容もセッション ID / 派遣した agent 名と整合していた)。

**その後、実作業は進んだ**。⟹ 残るのは「**報告と実態が一時的に乖離した**」という事実である。
⚠ **報告の内部整合性 (hash・行数・失敗理由まで具体的であること) は、成果物の実在を一切保証しない**。
⚠ **乖離は「無いものを在ると言う」向きだけでなく「在るものを無いと言う」向きにも起きる**。

⟹ **報告を成果物の証拠にしてはならない。`git log` / `ls` / ファイル本体で必ず裏を取る**。
⚠ これは idle 化した agent だけでなく**完了報告を返した agent にも等しく適用する** —
前 relay の処方 (「idle 通知が来たら直接検証する」) は**条件が狭すぎた**。
**idle かどうかは信号にならない**。

**(c) 派生する規約**: ブリーフ側に「**完了条件に成果物の実在を機械で示すこと**を含める」
(コマンドを列挙し、出力の貼り付けを要求する) を入れると、この失敗形は報告の段で露見する。
本 leg のブリーフはそれを実施した最初の例である。

## 7. scratchpad のセッション固有性が leg をまたぐたびに課金される

一次文献 (`pdftotext -layout` 済のテキスト) と数値検証器は**セッション固有の scratchpad**に
在る。metrics の「編集ファイル別」表がそのまま証拠で、`m8_*.py` / `m9_*.py` / `m10_*.py` /
`m11_*.py` / `m13/*.py` / `m14/*.py` / `m15/*.py` / `m6/*.py` が**5 つの異なるセッション ID の
下に散っている**。facts の各節が末尾に `$LIT` のパスと「消えていたら `## L0 (T3)` 節の URL から
再生成」を書いているのは、この課金を明示するためである。

⚠ **検証器を作り直すと 1 leg 溶ける**。本 relay では前 leg の検証器を `cp` で持ち越す運用
(metrics の `cp` 4 回) で凌いだが、**持ち越しの成否は leg のブリーフに明示的に書かれているかどうかに
依存していた**。⟹ **ブリーフに「前 leg の scratchpad の絶対パス」を書く**のが最も安い処方である。
