## 0. ゴール — 未解決本体そのもの

**一般 2 受信者 DM-BC の容量領域の計算可能な特徴付けを、肯定側か否定側のどちらかで決着させる。
散文の証明と、その Lean による機械検証の両方をもって完了とする。**

完了条件 (どちらか一方):

- **肯定側** — 任意の `ε > 0` に対し有界時間で `ε` 近似を返す手続きを構成し、その正当性を証明する。
- **否定側** — そのような手続きが存在しないことを証明する。

いずれの側も、**散文の証明が立つこと**と**Lean で proof done に到達すること** (0 sorry / 0 residual、
`#print axioms` が sorryAx-free、かつ署名走査で load-bearing hypothesis が無いこと) の両方を満たして
初めて達成とする。片側だけでは達成ではない。

### 0.1 ⚠ ゴール保護条項 — 本節は leg / planner が書き換えてはならない

**前 relay の前身で実際に起きた事故がこれである**。原案 (`487afc03`) は T2 の完了条件を
「文献に無い命題が **Lean で機械検証される**」と書き、「**ユーザー指定の二段構え
(散文で証明 → 形式化で検証)**」と明記していた。それを `28a740c5` が **L0 が走る前に**
「散文レベルの候補経路」へ書き換え、形式化をスコープ外にした。判断ログにはユーザー判断としての
記録が無い ⟹ **planner の独断でゴールが狭まり、20 leg がその狭いゴールで回った**。

したがって本 plan でも以下を規約とする:

1. **§0 のゴールと完了条件を狭める変更は、leg / planner が適用してはならない**。狭める提案は
   判断ログに **`GOAL-CHANGE`** として起票し、**ユーザーの承認を得るまで適用しない**。
   広げる方向 (より強い完了条件) は起票不要。
2. **中間結果は記録するが、ゴールの代替にはしない**。台帳 (facts / attacks / 在庫) への収穫は

   ゴールの設計からは外す** — ユーザーが「成果ゼロで終わる可能性を引き受ける」と明示的に選んだ。
3. **各 leg は冒頭に「この leg は §0 のゴールに対して何を動かすか」を 1 行で書く**。書けない leg は
   起票しない。⚠ **本 relay ではこの 1 行に「側」を併記させる** (§5.1)。

## 2. Approach

**三層を命題単位で回す設計は前 relay から有効なので引き継ぐ**。

```
層 1  散文        アイデア + 証明スケッチ
層 2  proof-probe 核 1〜2 ステップを機械検証 — 散文の自己欺瞞を最短で殺す装置
層 3  形式化      散文全体を Lean へ                            ← スコープ内
```

**⚠ 層 2 の道具を明示する**。T3 の主語は計算可能性なので、**数値掃引は原理的に効かない**
(有限の掃引は「有界時間で `ε` 近似できるか」を判定できない)。⟹ 本 relay の層 2 は次の 3 つに限る:

1. **小さな命題の厳密証明** (係数相殺・不等式の鎖など、掃引でなく計算で閉じるもの)。
2. **反例構成** — 明示 witness の直接評価。⚠ 最適化器の非違反は証拠として弱い (§4)。
3. **型検査 1 本の反証** — 「無い / 載らない / 足りない / 経由できない」と書いた瞬間に走らせる
   (§4 軸 1 の処方の実装)。⚠ **これは層 2 の主力である** — 前 relay の失敗 4 件はすべて
   反証コスト 1〜6 行だった。

**攻める順序 (relay 全体の形)**:

- **(C2) は §1 (ii) により 1 点へ還元されている**。⟹ 第一手は**その 1 点を両側から同時に測る** —
  厳密一致が成り立つか (肯定側) / 厳密な分離が出るか (否定側)。**どちらに転んでも軸が 1 本確定する**
  ので、gate として最も安い (§3)。
- 層 1 が通った命題は**その命題単位で層 3 へ載せる**。全体が揃うのを待たない。
- **⚠ 形式化の受け皿を M0 で先に測る** — (C2) の主張は「領域の計算可能性」なので、in-project に
  **平面集合版の計算可能性述語**が要る。スカラー版 `IsComputableENNReal` は Kolmogorov 家系に在る
  (facts `## L5 (T3)` 節)。⟹ **M0 でこの受け皿を結論形で数え直し**、無ければ (C2) の散文が
  立った時点で定義段を切る。⚠ 定義は教科書形の転記ではなく、**消費する Mathlib 補題の結論形から
  起こす** (CLAUDE.md「Mathlib-shape-driven Definitions」)。

### 4.2 在庫と証拠の作法 (3 規約)

- **在庫の「無い」は、家系でも検索語でもなく結論形で数える** — 結論パターン (`ConvexOn` 等) を
  project 全体に当てる (CLAUDE.md「In-repo asset search」)。
- **補題の再利用前に、署名だけでなく証明本体を読む** — 「結論に書いていない」は
  「証明していない」ではない。
- **loogle の生クエリのヒット数を「無い」の根拠にしない** — **結論形クエリを併記する**。
  生クエリの `Found n` は `n > 0` なら「在る」の誤証拠に、`n = 0` なら根拠の弱い「無い」になる。

### 4.3 検証の誠実性

CLAUDE.md の Definition of Done がそのまま効く (Standard B)。

- **`sorry` + `@residual(<class>:<slug>)` が唯一の honest な退出路**である。詰まったら署名を
  証明したい形のまま残し、body を `sorry` にする。本 relay の退出路の slug は
  **`@residual(plan:bc-open-problem-t3b-plan)`** (= 本ファイルの filename stem)。
  Mathlib の不足に当たった場合のみ `@residual(wall:<name>)` を立て、**register への追記を伴う**。
- **hypothesis に証明の核を担わせて `sorry` を消すのは禁止** (load-bearing hypothesis)。
  regularity precondition は可。
- **`sorryAx`-free は必要条件であって十分条件ではない** — 完了判定には**署名走査**
  (全 hypothesis が regularity precondition であることの確認) を必ず併せる。
- ⚠ **機械で再導出できる事実 (sorry の有無 / 宣言の存在 / axiom 依存) を本 plan の散文に
  キャッシュしない**。壁は `@residual(wall:<name>)` が**コード側の SoT** で、plan はスラグを参照する。
