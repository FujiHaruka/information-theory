# textbook-review: 教科書原稿を 4 観点で査読する

原稿の欠陥は層が違い、1 体に全部見せるとどの層も浅くなる。観点を分けると、観点ごとに
**違う SoT** に当たらせられる——数学は第1章の既出結果、形式化は Lean の実コード、規約は
`.claude/rules/textbook-writing.md`、読者体験は読者自身の頭。第2章の実測で 41 件出て、
観点をまたいで重複したのは 1 件だけだった（そしてその 1 件が唯一の BUG だった）。

## 起動条件

- 「教科書をレビューして」「第N章を査読して」「原稿をレビューさせて」
- 「章を複数観点でレビューして」「サブエージェントに査読させて」
- 「/textbook-review」（引数に章スラッグ。無ければ直近に触った章を確認する）

## 前提

- 原稿は `docs/textbook/`。第1・2章は `ch0N/` ディレクトリに 1 節 1 ファイル、
  第3〜5章は `ch0N-*.md` の 1 章 1 ファイル（`site/build.mjs` の `chapters` が SoT）。
- 執筆原則の SoT は `.claude/rules/textbook-writing.md`。**第1章が基準実装**。
- 査読エージェントは全員 **read-only**。修正はオーケストレーター（あなた）が当てる。
- CLAUDE.md「Parallel orchestration」の**同時 1 体キャップ**に従う。4 体は順に回す。
- コストは 4 体で合計 50〜60 万トークン規模（第2章の実測）。章の書き直し後・公開前など、
  節目で回すもの。

## やること

### 0. 対象を決め、機械検査を先に通す

章スラッグと節ファイルを確定する。次に機械検査を通してから査読に入る——**機械が見る層を
査読者に再走査させない**ため（査読の値打ちは機械が見ない層にある）。

```bash
deno run -A docs/textbook/site/build.mjs --audit-refs
./docs/textbook/site/vocab.ts <章スラッグ>
```

warn が残っていたら先に潰す。そのうえで、形式化観点に渡す Lean ファイルの一覧を作る。

```bash
rg -oIN '`[A-Za-z][A-Za-z0-9_/]*\.lean`' docs/textbook/<章>/*.md | tr -d '`' | sort -u
```

### 1〜4. 4 観点を順に回す

`references/briefs.md` の雛形を**そのまま**使い、`<章>` `<節ファイル一覧>`
`<Lean ファイル一覧>` `<既出章>` を埋める。1 体が完了してから次を出す。

| 順 | 観点 | `subagent_type` | `model` | 雛形 |
|---|---|---|---|---|
| 1 | 数学的正しさ | `general-purpose` | `opus` | ブリーフ A |
| 2 | 形式化との整合・正直さ | `general-purpose` | `opus` | ブリーフ B |
| 3 | 執筆原則への準拠 | `general-purpose` | `opus` | ブリーフ C |
| 4 | 読者体験 | `general-purpose` | `fable` | ブリーフ D |

読者体験だけ Fable なのは、これが検証ではなく**読者の頭のシミュレーション**だから
（他の 3 つは事実確認なので Opus）。

観点を減らすなら理由を持つこと。形式化ポインタを持たない草稿章ならブリーフ B は薄くなるが、
それでも「ポインタが無いこと自体」は §7 違反なので回す価値はある。

### 5. 指摘を統合する

- 重大度で並べる。BUG / FALSE / OVERCLAIM / VIOLATION が先、NIT は後。
- **観点をまたいで同じ指摘が出たら、それは強い信号**。独立な 2 体が別経路で同じ場所に
  着いたということなので、優先して確かめる。
- **重い指摘は自分で 1 度確かめてから直す。** 査読 verdict を額面で受け取らない
  （CLAUDE.md の doctrine）。反例だと言われたら自分で代入する。Lean の仮定の話なら自分で
  その行を読む。数値なら自分で計算し直す。査読者が間違っていることもある。
- 却下する指摘があれば、却下した理由を 1 行残してユーザーへの報告に含める。

### 6. 修正を当てる

**全観点が出揃ってから**着手する。査読中にファイルを動かすと、後続の査読者が古い行番号を
指し、指摘が読めなくなる。

- 章をまたぐ表記の割れが見つかったら、その場で直せる範囲（語の統一など）は直す。手が
  大きいもの（他章の構造変更）はユーザーに投げる。
- 規約と基準実装（第1章）が割れていることが判明したら、原稿ではなく**規約側を確定させる**
  のが筋。片方を採ってもう片方を消す（両論併記にしない）。

### 7. 判断を執筆原則に足す

査読で「規約に書いていなかったから割れた」と判明した点を
`.claude/rules/textbook-writing.md` に **原則 → 理由 → 判定法** の 3 点で足す（§0）。
判定法の書けない原則は足さない。§11 の乖離表に軸が増えたらそこにも行を足す。

### 8. 検査 → デプロイ → コミット

```bash
deno run -A docs/textbook/site/build.mjs --audit-refs   # warn 0 件
./docs/textbook/site/vocab.ts <章スラッグ>              # 原語混入 0 件
```

表示幅（全角 45 字 = 90 コラム）も確かめる。通ったら CLAUDE.md「Textbook site deploy」に
従って `docs/textbook/site/deploy.sh`、そのあと autonomous commit + push。

## 気をつけること

- **査読者に編集させない。** 雛形の「禁止」節を落とさないこと。編集を許すと、複数体が同じ
  ファイルを奪い合い、しかも誰の指摘だったか追えなくなる。
- **「よく書けている」を書かせない。** 総評は情報量ゼロで、指摘の枠を食う。雛形はすべて
  総評を禁じている。
- **判定法を実行させ、実行内容を書かせる。** 「§5 に適合」ではなく「このラベルを 1.6 節の
  第 3 段落に貼ったら成立した」と書かせる。書けないなら実行していない。
- **数値は再計算させる。** 「おそらく正しい」を禁じる一文を落とさない。
- 査読の指摘は原稿だけでなく、**規約・サイトのビルドスクリプト・第1章**にも及ぶ。スコープを
  決めるのはオーケストレーターの仕事で、査読者ではない。
