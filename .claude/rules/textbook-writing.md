# 教科書原稿 執筆原則

`docs/textbook/` に置く教科書原稿（第1・2章 = `ch0N/` の節ファイル、第3章以降 = `ch0N-*.md`）の
書き方の SoT。Lean コード側の規約は `docs/rules/` が SoT であり、こちらは**日本語の原稿**だけを
対象にする。進捗・章立ての管理は `docs/textbook-roadmap.md`、サイト生成は
`docs/textbook/site/README.md`。

**第1章が基準実装**である。迷ったら第1章の該当箇所を読んで合わせる（第2章も同じ規約に
揃えてあるので、章のまるごとの書き直しは第2章の差分が近い前例になる）。第3〜5章は草稿
段階で、割れている点が §11 の乖離表にある。

## 0. この文書を育てる

**原稿を書きながら下した判断は、原稿に埋める前にここへ書き足す。** これがいちばん上に来る原則。

- 暗黙のまま原稿に埋めた判断は、次の章で別の判断になる。実例：形式化ポインタが第1章
  `**形式化**:`、第2〜5章 `**Verified**:` に割れた（§11）。どちらも「正しく」書いたつもりで
  割れている。ここに 1 行あれば起きなかった。
- **ユーザーやレビューの指摘は、その場の修正で終わらせない。** 一般化して 1 項追加してから
  修正に入る。指摘は「この 1 箇所が悪い」ではなく「この判断軸が明文化されていない」の
  現れとして読む。
- 追加は **原則 → 理由 → 判定法** の 3 点で書く。判定法（何をどう見れば違反とわかるか）の
  ない原則は運用できないので、書けないなら原則として未成熟だと考える。
- 既存の原則と衝突したら、**勝つほうを残して負けたほうを消す**。両論併記にしない。
- 章をまたいで表記が割れているのを見つけたら、直せなくても §11 の乖離表に行を足す。
- ここが原稿の書き方の SoT。**原稿本文に執筆原則を書かない**（→ §3）。

## 1. 読者と前提

- 読者は Lean を知らなくてよい。原稿は自然言語と数式だけで独立して通読できること。
  形式化は「保証」として添えるものであって、読解の前提にしない。
- 予備知識は学部レベルの確率・解析まで。それを超える道具は本文中で組み立てる
  （第1章が有限 Jensen の不等式を凹性ただ一つから帰納法で組み立てているのが基準の粒度）。
- **道具を借りるときは、借りた先を明示する。** 「Jensen の不等式より」で済ませず、どの形で
  使うのかを書くか、その場で組み立てる。組み立てずに借りると決めたなら、その名前
  （「Cauchy の関数方程式」）と、以降のどこまでがそれに依存するかを書く。動機づけの中だけで
  借りていて定義から先は依存しない、という場合はそう書けば、読者はそこを追わなくてよいと
  分かる。
  - **判定法**：「〜が知られている」「〜しかない」と断定した箇所に、名前と依存範囲が
    添えてあるか。
- **借用宣言に書いた依存範囲は、章を書き終えてから照合する。** 「借りるのは定理 N.1.4
  だけ」と書いたあとで、別の節がその道具を直接使いはじめることがある。
  - **理由**：依存範囲の宣言は読者への約束で、外れていれば「ここから先は追わなくてよい」
    という読み方が壊れる。書いた時点では正しく、章が伸びた結果あとから偽になるので、
    書いた本人には見つけにくい。実例：第2章は大数の法則を「定理 2.1.4 だけで借りる」と
    宣言したが、2.4 節の強典型性が同じ法則を指示変数に直接当てていた。
  - **判定法**：借りた道具の名前で章内を検索し、宣言した範囲の外に使用がないか見る。
    あれば範囲の記述を直す（使用のほうを消してはいけない）。
- **借用宣言は、道具の主張の形まで特定する。** 名前と依存範囲だけでは足りない。
  - **理由**：形が曖昧なまま借りると、証明の側が勝手に強い形を使う。実例：第2章は
    「大数の法則——相加平均が期待値に収束する」とだけ宣言したのに、証明が弱法則と強法則を
    使い分けた。読者は「自分が認めたのはどちらだったのか」を確かめに戻ることになる。
  - **判定法**：その道具を使う行を読み、宣言に書いた形とそのまま噛み合うか。噛み合わない
    なら宣言をいちばん強い形に絞り、弱い形はそこから導く（二つ借りない）。
- **前提にしてよいのは、学部の確率・解析で全員が通る範囲まで。** 確率変数・独立・条件付き
  確率・期待値・一様分布やベルヌーイ分布は前提でよい。マルコフ連鎖・条件付き独立・統計量の
  ように履修が分かれるものは前提にしない。
  - **理由**：「学部レベル」は幅があり、読者の履修歴で割れる。割れる側に賭けると、その語を
    知らない読者は定義そのものが読めなくなる（§2 の前方参照違反と同じ症状が、章内の
    未定義語として出る）。
  - **判定法**：その語を初出の箇所で本文が定義しているか。していないなら、学部初年度の
    確率の教科書の目次に載る語かを問う。載らないなら定義を足す。
- **同じ語が分野によって別の意味を持つときは、本書でどちらの意味かを書く。** 前提知識の
  有無とは無関係に定義を置く。
  - **理由**：知っている読者ほど誤読する。第1章の「マルコフ連鎖」は三変数の条件付き独立を
    指すだけで、確率過程論の遷移行列・定常分布とは関係がない（そちらの意味は第3章で出る）。
    知識のある読者は時間発展する列を想起して、定義が何を言っているのか分からなくなる。
  - **判定法**：その語で検索して、本書の別の章が別の意味で使っていないか。使っていれば
    両方の箇所で意味を断る。
- **古典統計で定数として扱う量を情報量の引数に置くときは、確率変数として扱う旨を断る。**
  - **理由**：情報量は同時分布に対して定まるので、パラメータ $\theta$ に $I(\theta; X)$ と
    書いた時点で $\theta$ に分布を入れている。統計の作法では $\theta$ は未知の定数なので、
    断りがないと読者は「何の分布で平均しているのか」で詰まる。
  - **判定法**：情報量・エントロピーの引数に置いた記号が、その章で確率変数として導入
    されているか。されていないなら、分布を与える旨を 1 段落で断る。

## 2. 前方参照の原則

**その時点で未履修の用語を出してもよいが、それを説明の主にしてはならない。**

- 定義・証明・直感の説明は、**それまでに出た知識だけで完結する**こと。後述の概念を
  説明の依存にしてはいけない。読者が「まだ知らない言葉で説明された」と感じた時点で難しくなる。
- 未履修の用語は、**先の見通しを与える従の補足**としてのみ許す。
  例：「この形は 1.6 節で導入する相対エントロピーを使えば一行で書ける」
  「二値エントロピーは 1.10 節のファノの不等式でふたたび主役として現れる」。
- **判定法**：その未履修語を含む文を丸ごと削ってみて、定義／証明がなお成立するか。
  成立しないなら違反である。
- 違反したときの直し方は 2 通りで、この順に検討する。
  1. **既出の道具で書き直す**（多くの場合こちらで済む）。
  2. **節の順序を入れ替える**。節の並び自体が原則に反しているなら、断り書きを足すのではなく
     並べ替える。番号の振り直しは §8 の手順で行う。
- 節をまたぐ「あとで効いてくる」予告は歓迎する。禁じているのは予告ではなく、**依存**である。
- 予告を独立させたいときは `::: notation-preview` に隔離する（§5）。本文から浮かせて
  おけば、読み飛ばしてよいことが体裁で伝わる。

## 3. 章の構成

```
## N.1 …                    ← 節（1 節 1 ファイル）
## N.2 …
…
```

**章は本文から始める。読み方・範囲・保証を説明する案内のページ（章トビラ）を置かない。**
最初の節の 1 行目が、その章の 1 行目である。

- **理由**：案内は原稿ではなくサイトの説明であり、読者は本文を読みに来ている。章ごとに
  置くとどの章でも同じことが書かれ、読み飛ばされる枠が章の入口を占める。本全体に 1 度
  必要な説明——形式化ポインタが何を保証するか、アイコンがどこへ飛ぶか——は、本の入口
  である目次ページが持つ（`site/build.mjs`、→ §7）。
- **範囲と記法の限定は、それが効く場所で書く**（→ §10）。有限アルファベットの仮定は定義
  そのものに書き込めばよく、$\log$ の底は単位が要る箇所で断ればよい。章の全体にかかると
  思った限定ほど、実際には特定の定義・特定の主張にかかっている。
- **執筆原則そのものも書かない**（「なぜこう書いたか」「どう書くべきか」はこの文書が持つ）。
- **判定法**：章の最初のファイルの冒頭が、最初の節の動機づけの地の文になっているか。
  本書の読み方・保証・記法だけを述べた塊があれば、それが案内である。

**節ファイルの分割** — 章は 1 節 1 ファイルに割る（`ch01/01-entropy.md` …）。

- ファイル名は `NN-<英語スラッグ>.md`、`NN` は節番号。
- ファイル内の見出しレベルは、節タイトルが `#`、その下位が `##`。
- `site/build.mjs` の章定義に `sections` を足すとページ・目次・前後ナビが生成される。
- 節を入れ替えたらファイル名の `NN` と `build.mjs` の並びも揃える（順序の SoT は配列）。

## 4. 節の構成

節は次の順で書く。見出しは必要なものだけ立てる。

1. **文脈と動機** — 直前までに何を得たか、なぜ次の概念が要るか。
   `## 動機` のような見出しは置かず、節タイトル直後の地の文で書く。節が独立したページに
   なるため、ここが読者の入口になる。
2. **定義** — 記号を導入し、既出の言葉だけで読み下す。定義式を置いたら、**その式が何を
   言っているかを日本語で 1 段落**書く（式だけで放置しない）。
3. **例** — 最小の具体例（二値・一様・独立など）で値を確かめる。
4. **直感** — 式や証明が何を言っているか。§5 のとおり**地の文で書く**（ラベルを付けない）。
5. **命題・定理と証明**。

証明は **既出のものだけで閉じる**（§2）。閉じられないなら節の順序が間違っている。

**主張の根拠は `::: proof` に入れる。地の文で証明しない。**

- **理由**：読者は証明の付いていない主張を「著者が意図して証明を略した——この本では
  認めて使う——主張」として読む。根拠が直前・直後の地の文にあっても、体裁がそれを
  伝えない。§5 のとおり見出しと終端記号は環境から組まれるので、地の文に書いた証明は
  どこから始まってどこで終わったのかも読者に見えない。
- 主張の**前に**論証を流したくなることがある（「…だから次が成り立つ」）。それは
  動機づけであって証明ではない。動機づけは筋だけにとどめ、同じ論証を主張のあとに
  `::: proof` として書き直す。重複を恐れない。
- 帰納法・場合分けのように手筋を断りたいときはタグ行に足す
  （`::: proof $n$ についての帰納法`）。
- 主張と証明のあいだに補題を挟むときは、**その証明がどの主張のものかをタグ行で名乗る**
  （`::: proof 定理 1.1.5`）。終端記号（■ / □）もこの名前から決まる。
- 証明を付けないと決めた主張は、**そう決めたことを本文に書く**（何に依拠するのか、
  なぜ本書では証明しないのか）。黙って落とすと §10 の正直さに反する。
- **判定法**：`deno run -A docs/textbook/site/build.mjs` が証明の付いていない主張を
  `warn: 証明のない主張` として列挙する。0 件であること。

## 5. 環境タグと、直感の書き方

主張・証明・形式化ポインタ・傍注は `:::` のタグで囲む。**見出しはタグから組み立てられる**
ので、原稿には種別・番号・名前だけを書き、「定理 1.6.1（…）.」という文字列や証明末尾の
■ を手で書かない。体裁は `site/build.mjs` が持ち、原稿は Markdown のままにしておく
（GitHub でもそのまま読める）。型を増やすときは §0 に従ってここに登録してから使う。

| タグ | 用途 | 組まれる見出し |
|---|---|---|
| `::: theorem 1.6.1 情報不等式 / Gibbs` | 定理 | **定理 1.6.1（情報不等式 / Gibbs）.** |
| `::: proposition 1.3.2` | 命題 | **命題 1.3.2.** |
| `::: lemma 1.1.6 有限 Jensen の不等式` | 補題 | **補題 1.1.6（有限 Jensen の不等式）.** |
| `::: corollary 1.5.4` | 系 | **系 1.5.4.** |
| `::: definition 1.3.1 相互情報量` | 定義 | **定義 1.3.1（相互情報量）.** |
| `::: example 1.1.2 ベルヌーイ分布` | 例 | **例 1.1.2（ベルヌーイ分布）.** |
| `::: proof` | 証明 | **証明.** と、末尾の ■ |
| `::: proof $n$ についての数学的帰納法` | 手筋を断る証明 | **証明（$n$ についての数学的帰納法）.** |
| `::: proof 定理 1.1.5` | どの主張の証明かを名乗る | **証明（定理 1.1.5）.** |
| `::: formalized` | 形式化ポインタ（→ §7） | **形式化**: |
| `::: formalization-note` | 本文と Lean のルート差・型の都合（→ §7） | **形式化上の注記.** |
| `::: notation-preview` | 未履修記法の予告（→ §2） | **記法の先取り.** |

閉じは `:::` 単独行。守るのは 4 つ。

- **番号と名前はタグ行に置き、本文には主張だけを書く**。名前に丸括弧は付けない（組むときに
  付く）。名前の中で数式を使ってよい。
- **証明の終端記号は書かない**。■ と □ の別は、直前に現れた主張が補題かどうかで決まる。
- **傍注（形式化上の注記・記法の先取り）には読み飛ばせるものだけを入れる**。本文から浮いた
  体裁で組まれるので、本筋を入れると読み飛ばされる。バリアントはタグ行に足す
  （`::: formalization-note 本章共通` → **形式化上の注記（本章共通）.**）。
- **タグの外に決まり文句を手書きしない**。地の文に `**定理 1.2.3.**` と書いてもただの
  太字にしかならない。
- **主張の中の自由変数は、主張の中で量化する**。節の冒頭や定義で導入した記号でも、
  主張ブロックは単独で読めなければならない。
  - **理由**：量化子が主張の外にあると、読者は「任意の $\varepsilon$ について」なのか
    「ある $\varepsilon$ について」なのかを主張だけからは決められず、定義まで戻ることに
    なる。同じ主張の中で $\delta$ や $\eta$ だけが明示的に導入されていると、非対称が
    かえって目立つ。
  - **判定法**：主張ブロックだけを切り出して読み、現れる記号の量化子がすべて決まるか。

`**面積として読む.**` `**符号長で読む.**` のような地の文の太字リードはタグではない
（→ 次項）。引用ブロック（`>`）は用途がタグに移ったので、原稿では使わない。

**字下げは注釈にだけ使う**。主張と証明は本筋なので、左罫線も字下げも付けない。狭い画面では
1 文字分のインデントが効いて読みにくくなり、本文の左端が揃わない。主張どうしの区別は見出しの
色と前後の余白で付ける。字下げてよいのは読み飛ばせるもの——形式化ポインタと傍注——だけで、
そこでは字下げ自体が「本筋から外れている」という合図になる。型を増やすときも同じ線で引く。

**判定法**：`deno run -A docs/textbook/site/build.mjs` を回し、該当箇所の見出しが色付きで
組まれているか（主張）／末尾に ■ が付くか（証明）／薄い地色になるか（形式化ポインタ）。
ならないなら型から外れている。

### 直感は地の文で書く

**直感の説明に「きもち」「直感」「何がうれしいか」のような一般語のラベルを付けない。**
定義や定理の直後に、地の文としてそのまま続ける。

- **理由**：直感は本文の一部であって、別枠の付録ではない。ラベルで囲うと「読み飛ばして
  よい補足」に見えるが、実際にはそこがいちばん読んでほしい箇所である。「きもち」は
  内輪の言葉で、読者にはその枠が何をするものか伝わらない。
- **「うれしさ」を名乗るラベルも一般語である。** 「何がうれしいか」は具体的に見えるが、
  名指しているのは*読者にとっての利得*という抽象で、どの段落の頭にも置ける。すなわち
  何も名指していない。ラベルが可なのは段落の**視点**（面積で読む／符号長で読む／両端で
  確かめる）を名指すときで、段落の**価値**を予告するときではない。
- 地の文にすると書き出しを毎回考えることになるが、それでよい。「この定理は…と読める」
  「読み方は素直で…」「両端を見ておく」「この証明の要点は一つだけである」のように、
  **何をしようとしている段落なのかが最初の一文でわかる**書き出しにする。
- 太字リードを付けてよいのは、**その段落が何をするかを名指せるとき**だけ。
  `**面積として読む.**` `**符号長で読む.**` `**両端で確かめる.**` `**典型例.**`
  `**規模感.**` `**距離ではない.**` のように、視点の切り替えを具体的に言うものは可。
- **判定法**：太字リードだけを読んで、その段落が何をするか分かるか。分からない
  （「きもち」「直感」「注意」「補足」「何がうれしいか」のような一般語）なら、ラベルを
  外して地の文にする。別の言い方をすると、**そのラベルを別の節の別の段落の頭に貼っても
  成立するなら一般語**である。
- 同じ役割の段落に別々の名前を付けない（同じ章の中で「符号長で読む」と
  「符号長で読むと」を混在させない）。

## 6. 数式と記法

- **新しい原稿は `$…$` / `$$…$$` で書く。** LaTeX 括弧デリミタ `\(…\)` / `\[…\]` は
  第2〜5章の既存分にのみ残る（`build.mjs` の `normalizeMath()` が `$` 記法へ寄せている）。
- ディスプレイ数式は `$$` を独立行に置き、**閉じ行のあとに句読点（。、）を置かない**。
  式のあとの文は「…である。」のように地の文で続ける。数式の内部末尾の `,` `.` は、
  そこで文が切れるか続くかを示す区切りとして置いてよい（第1章が一貫してそうしている）。
- 記号は初出の定義で固定し、章の中で変えない。$\log$ の底は原則として固定せず、単位が
  要る箇所でだけ断る。
- **底を固定する必要が章のどこかで生じたら、章の最初の節で 1 度だけ断る。** 節ごとに
  繰り返さない。
  - **理由**：$2^{nH}$ のように指数と対数の底をそろえる必要は、たいてい章の全体に及ぶ。
    節ごとに断ると、同じ約束が章内で 3 度も 4 度も現れ、しかも先に書いた節が別の底で
    書かれたまま残る（第2章は 2.2 節で底を断りながら、2.1 節が既に $2^{nH}$ と
    $e^{-nH}$ を混ぜて書いていた）。
  - **判定法**：「$\log$ の底」を含む断りが 1 章に 2 度以上出ていないか。出ていれば、
    最初の節にまとめて残りを消す。
- **例で使う記号は、直前の定義が束縛変数に使っている文字を避ける。**
  - **理由**：定義が $\forall a \in \mathcal X$ と書いた直後の例で
    $\mathcal X = \{a, b, c\}$ と置くと、同じ $a$ が「任意の文字」と「特定の文字」の
    二役になる。読者は定義を読み返して衝突に気づくまで止まる。
  - **判定法**：例の中の記号を、その節の定義のタグ行から本文までに現れる束縛変数と
    突き合わせる。衝突したら例のほうを変える（$\{0,1,2\}$ のように数字に逃がすのが早い）。
- **数式に語らせない。** 式を出したら、その式が何を主張しているかを日本語で必ず添える。
- Lean の識別子・ファイルパスは行内 code（`` `entropy_nonneg` ``）で書く。日本語の文中に
  裸で置かない。
- **英語の術語を地の文に裸で置かない。** 訳語があるものは訳語で書き（像測度、記憶のない、
  エントロピー表現）、原語も示したいときは初出で括弧に併記する（「記憶のない（memoryless）
  通信路」）。形式化上の注記の中でも同じで、例外は Lean の識別子・ファイルパス（行内 code）
  と、訳語の定まらない術語だけである。
  - **理由**：訳語のある語を原語のまま置くと、同じ概念が章内で二つの名前を持つ。実例：
    像測度と push-forward、エントロピー表現と entropy 表現が同じ章に並んでいた。読者は
    別物かどうかの判断を強いられる。
  - **判定法**：行内 code と数式を伏せたうえで英字の連なりを拾い、残ったものが固有名詞・
    環境タグ・初出の原語併記・訳語のない術語のどれかであることを確かめる。
- **候補が複数あるときは、日本語で普及している語を採る。** 上から順に見て、当てはまった
  ところで決める。
  1. **日本語で定着した訳語があるなら、それ。** 十分統計量（充足統計量ではなく）、
     相対エントロピー、像測度、データ処理不等式。分野によって普及語が割れるときは、
     本書の分野——情報理論——の慣行に従う（相対エントロピーと KL ダイバージェンスは
     機械学習では後者が優勢だが、本書は前者を採る）。
  2. **訳語が定着していない、または原語のほうが通りがよいなら原語。** i.i.d.、pmf。
     カタカナに開くのは、対になる語がカタカナのときだけ（ビットに対するナット）。
  3. **人名は常にラテン文字。** Jensen、Cauchy、Gibbs。カタカナに開かない。
  4. **略語は導入しない。** データ処理不等式を DPI と略さない。原語の略語そのものが
     普及の単位になっている場合（i.i.d.）だけ例外。
  - **理由**：読者が既に知っている語で書けば、その語の説明が要らない。普及していない訳語は、
     正しくても読者には新語になり、覚える負担だけが増える。
  - **判定法**：候補それぞれで日本語の教科書・講義資料が引けるか、どちらが多く使われて
     いるかを見る。機械では決まらないので、選んだ理由を `terminology.mjs` の `why` に残し、
     次に迷ったときの前例にする。
  - 対象は術語であって、「エントロピー表現」のような普通の言い回しではない。
- **本書が名づける語は、外の標準名と突き合わせてから採る。既に採った語を部品にするときは
  縮約しない。** 節タイトル・主張名・定義した太字が「名づけた語」で、造語になりうるのは
  そこだけである。
  - **理由**：名づけた語はそのまま読者の検索語になる。標準から外れた名前を付けると、読者は
    本書の外の文献と結びつけられない。しかも縮約形は章の中では一貫して見えるので、原稿の
    中だけを読んでいるかぎり気づけない——既出語との突き合わせを何度やっても出てこない。
    実例：地の文が「情報源」と書き続けているのに、定理名だけ「源符号化定理」と縮んでいた。
    標準は「情報源符号化定理」で、対になる第4章が「通信路符号化定理」と標準どおりだったため、
    二つの定理の名前だけが非対称になっていた。
  - **判定法**：`./docs/textbook/site/vocab.ts <章スラッグ>` の**本書が名づけた語**を 1 語ずつ読み、
    (a) その語で日本語の教科書・講義資料が引けるか、(b) 語の部品が既出の語形とそのまま
    一致するか（「情報源」を「源」に縮めていないか）を確かめる。
- **新しい節を書いたら `docs/textbook/site/vocab.ts` を回す。** `terminology.mjs` の検査は
  既に表にある語しか見つけられないので、**未知の揺れを見つける経路はこれだけ**である。
  `./docs/textbook/site/vocab.ts <章スラッグ>` の出力は 3 つ。**原語混入**は規則が明確なので
  そのまま直す（第1章は 0 件を保つ。第2〜5章は草稿で、触るときに合わせる）。**本書が名づけた
  語**は節タイトル・主張名・定義の太字だけを集めたリストで、章あたり 20 語前後にしかならない。
  ここは既出語どうしではなく**外の標準名と**突き合わせる場所である（前項）。**章ごとの初出
  術語**は判定なしのリストで、既出の語と同じ概念を別の語で書いていないかを目で探す。
  見つけたら `terminology.mjs` に 1 行足す。以後は `build.mjs` が毎回守る（採用語が禁止語を
  丸ごと含む縮約形——「情報源符号」に対する「源符号」——も 1 行でよい。検査は採用語を先に
  伏せてから探す）。
  - **字面の近さで機械判定させようとしないこと。** 共通接尾辞のクラスタリングを試したが、
    候補 31 組すべてが偽陽性で（「結合エントロピー ~ 相対エントロピー」のような別概念）、
    実際の揺れ（充足統計量 ~ 十分統計量）は 1 組も出なかった。名づけた語の側でも一度試した
    ——本文の頻出語を縮約した形になっていないかを見る検査で、当たり（源符号化定理 ~ 情報源）は
    出たが、同時に「レート ~ エントロピーの『ー』」のような偽陽性が 107 組出て埋もれた。
    同義かどうかも縮約かどうかも意味の問題で、字面とは相関しない。機械の仕事は、候補を目で
    読めるサイズに減らすところまでである。
  - **判定法**：新しい節を含む章のスラッグで回し、原語混入が 0 件で、初出術語のリストに
    目を通したこと。
- **用語の採否は `docs/textbook/site/terminology.mjs` が SoT。この文書には語を書かない。**
  表記が割れた語を見つけたら、ここに原則を足すのではなくあちらに 1 行足す
  （`build.mjs` が毎回検査し、`warn: 表記ゆれ` として列挙する）。
  - **理由**：原則と、原則が参照するデータを同じ場所に置くと、増え続けるデータ行に原則が
    埋もれる。語は揺れを見つけるたびに増えるが、原則が増えるのは判断を下したときだけで、
    更新の頻度も理由も違う。
  - **判定法**：`deno run -A docs/textbook/site/build.mjs` の `warn: 表記ゆれ` が 0 件であること。

## 7. 形式化との対応

- 主要結果には §5 の `::: formalized` を添える。対応先は
  **無条件の機械検証済み定理**（`0 sorry` かつ `0 @residual`）に限る。
- **形式化ポインタは、その主張の直後に添える。節末にまとめない。**
  - **理由**：§7 のとおり原稿はパスを表示しないので、節末に並べたブロックは読者から見ると
    宣言名の羅列でしかなく、どれがどの主張のものかを日本語のラベルから手で対応づける
    ことになる。`.lean` のファイル境界を理由にブロックを分けると、読者には理由の見えない
    2 連続ブロックになる（第2章が一度そうなった）。主張ごとに置けばファイル境界の問題も
    消える。
  - **判定法**：`::: formalized` の直前が、そのポインタが指す主張か、その主張の証明・解説か。
- **Lean のコードを原稿に載せない。** 宣言のシグネチャも証明も引用しない。原稿が書くのは
  §7 のとおり宣言名とファイルパスだけで、掲載先へはビルドがリンクを張る。
  - **理由**：§1 のとおり読者は Lean を知らなくてよい。シグネチャを本文に置くと、読者は
    それが読解に要るのかどうかを毎回判断させられる。型クラス前提や `Measure Ω` の
    引数列は、日本語の証明の中では意味をもたない記号の塊にしかならない。加えて
    シグネチャは原稿にキャッシュされた事実であり（§7）、引数が 1 つ増えるたびに腐る。
  - **形式化の都合を伝えたいときは `::: formalization-note` に日本語で書く**（どの仮定が
    regularity で、本文のどの一行に対応するか）。コードを貼るより短く、腐らない。
  - **判定法**：原稿に ```` ```lean ```` のコードフェンスが無いこと**に加えて**、
    `$…$` の中に Lean の識別子・仮説名・`μ.map` のような式が入っていないこと。数式に
    入れると実在検査にもコードフェンス検査にもかからず、両方をすり抜ける（第1章が
    `IsMarkovChain` の定義本体と仮説名 $h_{\mathrm{iid}}$ を数式で引用していた）。
- **合成でしか得られない主張には `::: formalized` を付けない。** 本文の主張に対応する
  単独の宣言が形式化されていないなら、`::: formalization-note` に「単独の宣言はなく、
  どれとどれの合成で得られるか」を書く。
  - **理由**：形式化ポインタは「この主張がそのまま機械検証されている」という保証として
    読まれる。合成が必要な主張にポインタを付けると、その保証を実際より強く見せることに
    なる。合成の事実そのものは有用なので、隠すのではなく注記に落とす。
  - **判定法**：`::: formalized` の中の宣言名それぞれについて、その宣言の結論が本文の
    主張と（型の差を除いて）同じ形か。違うなら注記に移す。
- 本文の証明と Lean の証明ルートが実質的に食い違う箇所は `::: formalization-note` で正直に断る。
  保証するのは**定理の正しさ**であって、紙の証明手順の一致ではない。ルートが違うこと自体は
  欠点ではないので、隠さず、詫びず、事実として書く。
- 形式化の都合（`ℝ≥0∞` と `ℝ` の型差、`StandardBorelSpace` などの regularity 前提）は
  注記に隔離し、本文の数学からは追い出す。**regularity 前提と定理の核心を混ぜない**
  （核心を仮定に抱えた declaration は、そもそも紐付け先にしてはいけない）。
- **機械で再導出できる事実を原稿にキャッシュしない。** 「本章作成時点でこのファイルは
  `sorry` を含まない」のような記述は、書いた瞬間から腐り、誰も無効化しない。原稿には
  「`0 sorry` かつ `0 @residual` を満たすものだけを紐付ける」という**方針**を書き、
  現在値は `#print axioms` / `rg` で引く（CLAUDE.md「再導出 > キャッシュ」と同じ）。
- **宣言名とファイルパスを行内 code で書くだけにし、リンクは原稿に書かない。** `build.mjs` が
  `::: formalized` の中の行内 code を掲載先に変える——宣言名は API ドキュメントのその項目へ、
  パスは GitHub のソースへ飛ぶ。
  - **理由**：§8 の番号参照と同じで、原稿が掲載先の URL を知らずに済む。宣言が別ファイルへ
    移っても、名前空間が変わっても、原稿には手を入れずに追随する。手で URL を書くと、
    リポジトリの再編のたびに全ポインタが腐る。
  - **リンクの基準はリリースタグである**（`git describe --tags --abbrev=0`、`TEXTBOOK_REF` で
    上書きできる）。ソースリンクはタグに固定されるので、あとのリネームでは腐らない。宣言表も
    タグ時点のソースから組むため、まだリリースに入っていない宣言はリンクにならず warn に出る
    ——「リリース済みの機械検証済み定理だけを紐付ける」という §7 の方針が、ここで機械化される。
    API ドキュメントだけは 1 版しか置けず常に最新リリースを指すが、同じブロックにタグ固定の
    ソースリンクが並ぶので、行き先は残る。
  - 同じ短い名前の宣言が複数あるとき（`condEntropy` は 3 つある）は、同じブロックが名指しする
    パスで絞る。だから**宣言名にはファイルパスを併記する**。絞れないときは warn に出る。
  - **パスは表示されない。** 原稿には従来どおりファイルパスを書くが、掲載時は「ソース」という
    共通の語に置き換わる（行の中でいちばん長いのに、読者には用がないため）。**宣言名はそのまま
    出す**——読者が名前を知る手がかりであり、1 ブロックに 2 つ以上並ぶとき互いの区別も担う
    （「主定理 …、等号条件 …」）。原稿が書いたパスはホバーと読み上げに出る。
  - **2 つの行き先はアイコンで見分けさせ、原稿には行き先の語を書かない**（解説ページ＝本、
    ソース＝GitHub のマーク）。意味は目次ページで本全体に 1 度だけ説明する（`build.mjs`）。
    - **理由**：ポインタごとに「解説」「ソース」と書くと、宣言が 2 つ並ぶブロック
      （「主定理 …、等号条件 …」）では語が 4 つ出て、日本語の文としてうるさくなる。
      §5 と同じで、体裁は `build.mjs` が持ち、原稿は名前だけを書く。
    - **判定法**：`::: formalized` の中に「解説ページ」「ソース」「〜を参照」のような
      行き先を指す語が無いこと（「参照分布」のように術語の一部である場合は当たらない）。
      ホバーと読み上げには `build.mjs` が役割を語で出している。
  - **行番号を書かない**（`MIChainRule.lean:93` のように指さない）。宣言名を書けば掲載先へ
    飛ぶので行番号は要らないし、行番号は宣言が 1 行動くだけで腐る（実例：この規則を書いた
    時点で、原稿にあった 2 つの行番号ポインタはどちらも証明の途中を指していた）。
    §7 の「機械で再導出できる事実を原稿にキャッシュしない」が、ここにも効く。
  - **判定法**：`deno run -A docs/textbook/site/build.mjs` が `warn: 形式化ポインタ` /
    `warn: 注記の形式化ポインタ` を出さないこと（`::: formalization-note` の中に書いた
    宣言名とパスも、リンクにはならないが同じ実在検査を受ける）。取りこぼし——リンクになるべきなのに素通しされた語——は
    `--audit-refs` の「リンクにならなかった形式化ポインタの語」で目で確かめる（§8 の参照監査と
    同じ考え方）。残ってよいのは Mathlib の名前と、名前空間そのものの言及だけである。

## 8. 番号と相互参照

- 番号は `定義 1.3.1` / `定理 1.4.2` のように 章.節.通番。節内で定義・命題・定理・補題を
  種別によらず通し番号にする。
- 参照は番号で行う（「定理 1.2.3 より」）。「先ほどの定理」「上の補題」で参照しない。
- **参照は決まった形で書き、リンクは原稿に書かない。** 本文の「定理 1.2.3」「1.6 節」
  「第2章」は `build.mjs` が掲載先へのリンクに変える（主張には `#thm-1.2.3`、節見出しには
  `#sec-1.6` の id が振られる）。
  - **理由**：番号だけを書けば、その主張がどのページにあるかを原稿が知らずに済む。節を
    別ファイルに割っても、章を 1 ページに畳んでも、参照元は書き換えずに追随する。手で
    リンクを書くと、この独立が失われて、移動のたびに全参照が腐る。
  - 拾われるのは 3 つの形だけである。**主張**＝種別（定理・命題・補題・系・定義・例）＋
    章.節.通番（`定理 1.2.3`）、**節**＝章.節＋「節」（`1.6 節`）、**章**＝`第2章`。
    あいだの空白は空けても詰めてもよい。行内 code・数式・見出し・`:::` のタグ行は
    参照とみなさない（`` `定理 1.1.5` `` はリンクにならない）。
  - **判定法**：`deno run -A docs/textbook/site/build.mjs` が `warn: 未解決の参照` /
    `warn: 参照の種別ちがい` / `warn: 番号の重複` / `warn: 自節への参照` を出さないこと。
- **番号には必ず種別を添える。裸の番号を書かない**（「1.1.5 の信頼の底」ではなく
  「定理 1.1.5 の信頼の底」）。
  - **理由**：読者は飛ぶ前に、飛び先が定理なのか定義なのかを知りたい。加えて、裸の番号は
    数値と字面が同じで（本文には「約 2.58 ビット」のような数が出る）、機械にも人にも
    参照だと判別できない。種別が、番号を番号として読ませている。
  - **判定法**：`warn: 種別のない参照` が 0 件であること。実在する番号が種別なしで
    現れたときだけ出る（数値は素通しになるので、この検査だけでは足りない。次項）。
- **取りこぼしがないことは監査モードで確かめる。**
  `deno run -A docs/textbook/site/build.mjs --audit-refs` が、参照になりえたのにリンクに
  ならなかった数字を並べる。
  - **理由**：「2.58」が数値で「1.10」が節番号であることは、字面では決まらない。だから
    機械には判定させず、目で読めるサイズまで候補を絞らせる（§6 の `vocab.ts` と同じ
    考え方）。この一覧を通さないと、「節」を書き落とした参照が黙って地の文に埋もれる。
  - **判定法**：一覧に残るのが数値だけであること。節番号・定理番号が残っていたら、
    それは参照の書き方が §8 から外れている。
- **番号を振り直すときの手順**：
  1. 番号を付け替える。新旧が衝突する付け替え（1.4 ↔ 1.5 など）はプレースホルダを挟んで
     2 段で置換する。
  2. ビルドを回し、`warn: 未解決の参照` が挙げた行を直す（参照元を `rg` で洗う作業は
     この検査が肩代わりする。番号だけを直して参照を直し忘れると、そこが warn に出る）。
  3. もう一度 §2 の前方参照チェックを回す（順序を変えると依存の向きが変わる）。
- 自分の節番号を自己参照しない（1.6 節の本文に「1.6 節の情報不等式」と書かない）。
  「本節」「次節」「前節」は使ってよい。ビルドが `warn: 自節への参照` で拾う。
- **傍注は参照しない。** `::: formalization-note` / `::: notation-preview` には番号が
  振られないので、「上記の注記のとおり」「本節末の注記」と位置で指すことになる。
  - **理由**：位置参照は §8 が禁じている形そのもので、しかも傍注は読み飛ばせるものと
    決めた枠（§5）だから、本文がそこへ読者を送る時点で枠の約束が壊れる。
  - **判定法**：「注記」という語が傍注の外に出ていないか。出ていたら、同じ内容を
    その場に書き直す（重複を恐れない）。それが長すぎるなら、本文に上げるべき内容である。

## 9. 日本語の書き方

- 表示幅 90 コラム（全角 45 字）程度で、**文の切れ目・句読点で改行する**。単語の途中や
  数式の途中で折らない。1 文 1 行にはしない（差分が読みにくくなる）。
- **和文の改行位置は表示に影響しない**。`site/build.mjs` が前後どちらかが和文の soft break を
  落とすため、原稿でどこに改行を入れても出力に空白は入らない。改行位置は差分の読みやすさだけで
  決めてよい。ただし**欧文どうしの折り返しでは空白が残る**（宣言名やパスの並びなど）ので、
  そこは語の境界で折る。
- 常体（である調）。敬体と混ぜない。
- 数式と日本語のあいだに空白を入れない（`$X$ が` であって `$X$　が` ではない）。
- ダッシュは `——`（全角 2 つ）。三点リーダは `…`。
- 「〜のようなもの」「〜と言えるだろう」のような逃げを書かない。断定できないなら
  何が未解決かを書く（§7 の正直さと同じ姿勢）。

## 10. 正直さは、書いたその場で担保する

スコープ外にしたこと・形式化が及んでいないことは、**それが問題になる場所で**書く。
章末に「この章で扱わなかったこと」の一覧を置かない。

- **主張ごとの限定は、その主張の場で書く**。証明を付けないと決めたならそう書き（§4）、
  形式化ポインタは無条件の機械検証済みのものだけに付け、本文と Lean のルート差は
  `::: formalization-note` で断る（§7）。ここまでやれば、章末に繰り返すことは残らない。
- **理由**：章末の一覧は、本文で既に言ったことの再掲になるか、書かなかったこと——無限に
  ある——の恣意的な列挙になるかのどちらかにしかならない。前者は二重管理で腐り、後者は
  網羅できないので正直さの担保にならない。実例：第1章の章末注記は 3 項のうち 2 項が章
  トビラの再掲で、残る 1 項は「ファノの不等式の系を網羅していない」という、本文がそもそも
  主張していないことの否定だった。
- **判定法**：書こうとしている限定が、対応する主張の近くで既に言われていないか。言われて
  いれば重複であり、言われていないなら**その場所に書く**。どちらでもない——章末にしか
  置けない——なら、それは原稿ではなく `docs/textbook-roadmap.md` が持つ予定の話である。

## 11. 章ごとの現状と乖離

第1章が基準実装で、第2章も同じ規約に揃えてある。第3〜5章は草稿段階で、以下が
割れている。触るときに合わせていく。

| 軸 | 第1・2章（基準） | 第3〜5章（草稿） |
|---|---|---|
| 形式化ポインタ | `::: formalized` タグ | `**Verified**: …` 地の文 |
| Lean コード | 載せない（宣言名だけ） | 定理ごとに Lean のシグネチャを引用（§7 違反） |
| 章の入口 | 案内を置かず本文（N.1 節）から始まる | 「このファイルについて」ブロック＋作成時点の `sorry` 状況をキャッシュ（§3・§7 違反） |
| 章末 | 注記を置かない（限定はその場で書く） | 「未形式化項目・作業所見」を章末に列挙（§10 違反） |
| 定義・定理の番号 | `::: definition 1.3.1` の通し番号 | 番号なし（節見出しへの参照だけが張れる） |
| 主張と証明 | すべての主張に `::: proof` | 証明を置かず、Lean の存在で代える |
| 数式デリミタ | `$…$` / `$$…$$` | `\(…\)` / `\[…\]` |
| 直感の書き方 | 地の文 + 視点を名指す太字リード | 直感の記述自体が薄い |
| 節ファイル分割 | 分割済（`ch01/`・`ch02/`） | 1 章 1 ファイル |
| 前方参照（§2） | 検査済 | 未検査 |
